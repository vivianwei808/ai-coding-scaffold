用户要求进行一次**复盘**。你需要提出对编码 agent **环境**的改进建议，让后续运行更有效。

## 步骤

1. 调用 Skill 工具加载 `writing-for-agents`，作为写作风格指南。

2. 阅读用户指定会话的一手资料。这可能需要搜索本机的会话日志。如果用户没有指定会话，默认复盘当前会话。

3. 从以下类别中寻找改进候选项。

- **导航**：agent 是否容易找到正确文件？文件之间是否存在隐藏依赖？增加**导航指针**能否改善？当会话花费很长时间寻找某项信息时使用。
- **自动化检查**：是否存在能够捕获 agent 所犯错误的自动化检查，例如 lint、类型检查、测试或文件系统 linter？先阅读仓库自己的检查命令，包括 `package.json` 或构建工具的 `lint`/`check` 脚本及 CI 工作流。若检查已经存在但未接线或静默失效，问题在于接线，而不是重新发明检查。仓库完全没有**护栏**（没有 pre-commit hook，也没有运行 lint/typecheck/test 命令的 CI job）本身就是一项发现。未 lint 的仓库是持续存在的漏检机会，不是中性默认值。当自动化检查本可以捕获 agent 的错误，或仓库根本没有护栏时使用。
- **编码规范**：是否应该给**审查 agent**增加新规则？是否应该删除或澄清现有规则？先对违规进行分类。**机械性**违规（固定语法模式、禁用 API、import 形状、文件位置规则）必须使用确定性检查：仓库自身 linter 的自定义规则、新 pre-commit hook 或新 CI job，选择最符合仓库语言和现有护栏、成本最低的一种。默认构建检查，而不是编写规则。仅把真正需要**判断**的事项留在 `CODING_STANDARDS.md` 中，例如跨文件一致性、"匹配周边风格"以及任何护栏无法替代的规则。当审查 agent 未能发现错误时使用。
- **全局 AGENTS.md**：是否有任何引导指令应迁移到编码规范或自动化检查？当仓库或用户全局范围内的 AGENTS.md 特别庞大时使用。
- **工具经济性**：agent 是否执行了可以精简的昂贵工具调用？是否有自定义工具（CLI、MCP）特别浪费 token？当 agent 执行了昂贵工具调用时使用。
- **无效指令**：检查引导文件中没有改变 agent 行为的指令。当引导文件庞大而难以维护时使用。
- **信息访问**：寻找提升 agent 信息访问能力的机会，例如转存开发服务器日志、提供第三方服务的只读访问。当 agent 无法获得某项关键信息时使用。

4. 按严重程度从高到低向用户展示候选项。

## 参考

### 实现与审查

记住，所有工作都会经历两个阶段：实现和审查。实现 agent 承受最大的**上下文压力**，负责探索、编写代码和调试失败。

审查 agent 承受的上下文压力最小，因为它直接接收 diff，不需要探索，通常也不需要编写代码或调试。

因此，编码规范应由审查 agent 执行，而不是由实现 agent 执行。

### 文件

你可以访问仓库中的以下文件：

- `CLAUDE.md`/`AGENTS.md`：任何在该仓库工作的 agent 都会把这些文件推入上下文窗口。应极其克制地使用它们，通常只放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：该文件在审查阶段读取，而不是在实现阶段读取。如果规范文件超过 1,000 行，应增加指向 docs 目录的**导航指针**。
- Docs：将文档用作参考文件，并由其他文件指向它们。写新文档前先查找现有文档。
- Skills：将技能用于文档（因为其 description 会进入 agent 上下文窗口）或用户调用的命令。遵循 `writing-for-agents` 技能的建议。
