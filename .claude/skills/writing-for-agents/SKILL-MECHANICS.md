# 技能机制

[`writing-for-agents`](SKILL.md) 的技能专属分支：当文档是一个技能时的变化——前置元数据、调用方式选择以及路由技能。除此之外的所有写作规则，均适用 `SKILL.md` 中的通用参考。

## 调用方式（Invocation）

两种选择，在两种负载之间权衡：

- **模型调用（Model-invoked）** 技能保留 `description`，因此智能体可以自主触发，其他技能也可以触达它。你仍然可以手动输入它的名字：模型调用始终*包含*用户触达；一个 description 只会增加智能体发现，永远不会移除人为的。description 是技能顶级的上下文指针，被强制始终保持加载：永久上下文负载换取可发现性。一个内容全是参考的模型调用技能也是共享参考的一种归宿：另一个技能可以调用它，这样多个技能需要的参考就存在一个地方。机制：省略 `disable-model-invocation`，写一个面向模型的 description 并携带触发分支（`SKILL.md` 中的指针编写规则完全适用）。
- **用户调用（User-invoked）** 技能从智能体的触达范围中剥去 description：只有人类输入名称才能调用它，没有其他技能可以。零上下文负载，但消耗认知负载：你是那个必须记住它存在的索引。机制：设置 `disable-model-invocation: true`；`description` 变成面向人类的：一行摘要，触发列表被删除。

只有智能体必须自行触达、或另一个技能必须触达时，才选择模型调用。如果它只会手动触发，就设为用户调用，不付出上下文负载。

两个用户调用技能都需要的共享参考不能放在任何一个里：没有 description，谁都触达不了对方。把它推到技能系统之外的普通文件中：任何技能都可以指向的外部参考。

## 按调用拆分（Splitting by Invocation）

拆分的调用维度（顺序维度在 `SKILL.md` 中）：当你有一个独立的关键词应该自行触发它（一个你确实会在提示中使用的触发词），或另一个技能必须触达它时，拆分出一个模型调用的技能。你为新的常驻 description 付出上下文负载，所以独立的触达能力必须值得这个代价。

## 路由技能（Router Skills）

当用户调用技能多到超出你能记住的量时，堆积的认知负载由**路由技能**来治愈：一个用户调用的技能，命名其他技能以及何时使用每一个，这样人类只需记住一个技能而不是很多个。它只能提示，永远不能触发它们：用户调用技能没有 description，所以除了人类没有谁能触达它们。
