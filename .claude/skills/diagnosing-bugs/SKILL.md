# 诊断 Bug

一套处理棘手 bug 的纪律方法。只有在明确说明理由时才能跳过阶段。

探索代码库时，阅读 `GLOSSARY.md`（如果存在），建立对相关 module 的清晰心智模型，并检查当前区域的 ADR。

## 脱敏

此技能会展示命令、输出和捕获的产物。**先脱敏所有秘密**：用 `<REDACTED>` 替换。针对环境变量构建循环，让凭证留在环境中，而不是出现在展示内容里。捕获的产物携带认证头，只引用真正携带信号的行。

如果脱敏后的输出不足以诊断 bug，请说明并询问用户。

## 阶段 1：构建反馈循环

**这就是本技能的核心。** 其余步骤都是机械过程。如果你拥有一个针对该 bug 的**紧密**通过/失败信号，也就是一个能在*这个* bug 上变红的信号，就能找到原因。二分、假设检验和插桩都只是在消费它。如果没有反馈循环，再久的代码阅读也救不了你。

在这里投入不成比例的精力。**积极尝试，发挥创造力，不要轻易放弃。**

### 构建方式，按大致顺序尝试

1. 在能够触达 bug 的 seam 上写一个**失败测试**：unit、integration 或 e2e。
2. 针对正在运行的开发服务器编写 **curl / HTTP 脚本**。
3. 使用 fixture 输入执行 **CLI 调用**，并把 stdout 与已知正确的 snapshot 比较。
4. 使用**无头浏览器脚本**（Playwright / Puppeteer）驱动 UI，并断言 DOM、console 或 network。
5. **重放捕获的 trace。** 把真实网络请求、payload 或事件日志保存到磁盘，然后隔离地重放经过相关代码路径。
6. **一次性 harness。** 启动系统的最小子集（单个 service、mocked dependencies），通过一次函数调用触发 bug 路径。
7. **属性测试或 fuzz 循环。** 如果 bug 是“输出偶尔错误”，运行 1,000 个随机输入寻找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间（commit、dataset、version），自动化“在状态 X 启动、检查、重复”，以便运行 `git bisect run`。
9. **差异循环。** 用相同输入运行旧版本和新版本（或两套 config），然后比较输出。
10. **HITL bash 脚本。** 最后的手段。如果必须由人点击，用 `scripts/hitl-loop.template.sh` 驱动人类操作，让循环仍然结构化。捕获的输出会反馈给你。

构建正确的反馈循环，bug 就完成了 90%。

### 收紧循环

把循环当作一个产品。拥有一个循环后，继续**收紧**它：

- 能否让它更快？缓存 setup、跳过无关初始化、缩小测试范围。
- 能否让信号更精确？断言具体症状，而不是“没有崩溃”。
- 能否让它更确定？固定时间、设置随机种子、隔离文件系统、冻结网络。

一个耗时 30 秒且不稳定的循环只比没有循环稍好；一个耗时 2 秒且确定的循环才是调试利器。

### 非确定性 bug

目标不是得到一次干净的复现，而是获得**更高复现率**。把触发器循环 100 次、并行运行、增加压力、缩窄时序窗口、注入 sleep。复现率 50% 的 flaky bug 可以调试，1% 的不行。持续提高复现率，直到它可以调试。

### 确实无法构建循环时

停下来并明确说明。列出你尝试过的方法。向用户请求以下任一项：(a) 能复现问题的环境访问权限；(b) 已脱敏的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏）；(c) 添加临时生产插桩的许可。**没有循环时不要继续提出假设。**

### 完成标准：一个会变红的紧密循环

阶段 1 完成时，循环必须**紧密**且**能够变红**。你能说出**一个命令**（脚本路径、测试调用或 curl），已经至少实际运行过一次，并展示过脱敏后的调用和输出。它还必须满足：

- [ ] **能够变红**：它驱动真实的 bug 代码路径，并断言**用户报告的确切症状**，因此能在这个 bug 上变红，在修复后变绿。不能只断言“运行没有报错”，必须能捕获这个具体 bug。
- [ ] **确定**：每次运行给出相同结论。对于 flaky bug，按上文固定为较高复现率。
- [ ] **快速**：耗时几秒，而不是几分钟。
- [ ] **Agent 可运行**：能够无人值守运行。只有通过 `scripts/hitl-loop.template.sh` 才允许 human in the loop。

如果发现自己在该命令存在之前就开始阅读代码构建理论，**立即停止：直接跳到假设正是本技能要阻止的失败模式。** 没有能变红的命令，就不能进入阶段 2。

## 阶段 2：复现并最小化

运行循环，看着 bug 出现并变红。

确认：

- [ ] 循环产生了**用户**描述的失败模式，而不是附近另一个恰好出现的失败。复现了错误的 bug，就会修错问题。
- [ ] 多次运行都能复现；对于非确定性 bug，复现率足够高，可以作为调试依据。
- [ ] 已捕获确切症状（错误信息、错误输出、缓慢耗时），后续阶段可以据此确认修复真的解决了它。

### 最小化

循环变红后，把复现场景缩小到**仍会变红的最小场景**。每次只删除一个 input、caller、config、data 或 step，并在每次删除后重新运行循环。只保留对失败真正承重的部分。

这样做会缩小阶段 3 的假设空间（可疑活动部件更少），并为阶段 5 形成干净的回归测试。

当**每个剩余元素都不可缺少**时完成：删除任何一个都会让循环变绿。

在完成复现和最小化前，不要继续。

## 阶段 3：提出假设

在测试任何假设前，生成 **3 至 5 个按优先级排序的假设**。只生成一个假设会让你锚定第一个看似合理的想法。

每个假设都必须**可证伪**，并明确它会产生的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失，或者 <改变 Z> 会让它更严重。"

如果无法陈述预测，这个假设只是感觉：丢弃它，或者继续打磨。

**测试前向用户展示排序后的清单。** 用户通常拥有能立即改变排序的领域知识（“我们刚部署了与第 3 项相关的变更”），也可能知道哪些假设已经被排除。这是成本低、收益高的检查点。不要阻塞在这里；如果用户不在线，按你的排序继续。

## 阶段 4：插桩

每个 probe 都必须对应阶段 3 的某个具体预测。**每次只改变一个变量。**

工具优先级：

1. 如果环境支持，优先使用 **debugger / REPL 检查**。一个 breakpoint 胜过十条日志。
2. 在能区分不同假设的边界增加**定向日志**。
3. 永远不要“把所有东西都打日志再 grep”。

给每条调试日志加上唯一前缀，例如 `[DEBUG-a4f2]`。结束时只需一次 grep 就能清理。没有 tag 的日志容易残留，有 tag 的日志必须删除。

**性能分支。** 对性能回归而言，日志通常不是正确工具。先建立基线测量（计时 harness、`performance.now()`、profiler、query plan），然后二分。先测量，再修复。

## 阶段 5：修复并添加回归测试

**先写回归测试，再写修复**，但前提是存在一个**正确的 seam**。

正确的 seam 能让测试按照 call site 中实际发生的方式触发**真实 bug 模式**。如果唯一可用的 seam 太浅（bug 需要多个 callers，却只能测试单一 caller；需要完整调用链，却只能写 unit test），在那里写回归测试只会制造虚假信心。

**如果不存在正确的 seam，这本身就是发现。** 记录它。代码库架构正在阻止该 bug 被测试锁定。把它标记给下一阶段。

如果存在正确的 seam：

1. 把最小复现转化为该 seam 上的失败测试。
2. 看着它失败。如果你通过修改代码或 fixture 强制制造红灯，先与原始副本做 `diff`，证明该修改确实生效，再相信这个红灯。
3. 实施修复。
4. 看着测试通过。
5. 针对原始的、未最小化的场景重新运行阶段 1 的反馈循环。

## 阶段 6：清理

在宣布完成前必须确认：

- [ ] 原始复现不再出现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或者已记录 seam 缺失）
- [ ] 所有 `[DEBUG-...]` 插桩已删除（grep 该前缀）
- [ ] 一次性原型已删除（或移动到明确标注的 debug 位置）
- [ ] 已在 commit / PR 消息中写明最终被证实的假设，让下一位调试者能够复用结论
